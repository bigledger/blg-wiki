# Tax configuration

The tenant-wide list of tax codes. One row of `bl_fi_cfg_tax_code` per code: a unique code string, a description, a tax type, a rate and a country. It is master data only — no journal, no stock, no queue. Two things flow out of it: the tax drop-downs on document lines, and the rate the backend stamps onto a line when the document is saved. The account the tax posts to is **not** here; it comes from the company's default GL code links.

## How it connects

- **chart-of-accounts / organisation** — the real tax-to-account mapping is the company default GL code link (`OUTPUT_TAX`, `INPUT_TAX`), not anything on the tax code.
- **doc-item-maintenance / inv-item-maintenance** — items carry a default tax code that pre-fills the document line.
- **internal-sales-invoice-applet / internal-purchase-invoice-applet** and every other taxable document — read the list through the shared `app-sst` / `app-wht` line components.
- **e-invoice** — carries the stamped rate and amount; the LHDN tax *type* comes from the e-Invoice taxable-type code instead.
- **entity-applet / customer-maintenance / supplier-maintenance / merchant-admin** — hold per-entity tax registration numbers keyed by the same tax types; they do not restrict which codes a document may use.
- **MY-SST applet** — a second write surface over the same table with different country encoding, different rounding and a different tariff-code column. This is the main source of inconsistent rows.

## Open questions

- Which of the two write surfaces is meant to be canonical — Tax Configuration or the MY-SST applet's Tax Code screens? They disagree on `tax_country` encoding, rate rounding and where the tariff code is stored.
- Should `app-sst` include `VAT-SALES` on the sales side? As written, tenants in Singapore, Thailand and Indonesia cannot pick their sales VAT code on a document line.
- Is anything meant to read `is_input` / `is_output`? They are maintained by both applets and consumed by nothing.
