# User Permission Manager (Website Builder)

The Webstore dashboard tile that grants and removes CP Commerce Admin access for a storefront. It verifies an e-mail address against the platform's login accounts, optionally invites the person to create one, then installs the CP Commerce Admin applet for them and links them to one tenant role. It is a feature of the storefront app, not an applet: there is no registry row for it.

## Facts

- 2026-09-06 — The code lives in the storefront app, not in the admin applet: `src/app/pages/website-builder/webstore/user-permission-manager/` in `wavelet-cp-commerce` (base app @247243251; component last touched @79a8864bd, 2026-07-21). None of the per-customer forks of that app contain it. [src:refs/wavelet-cp-commerce/src/app/pages/website-builder/webstore/user-permission-manager/user-permission-manager.component.ts] [src:customer-repo-1322ac#177]
- 2026-09-06 — No registry row under any plausible name (`user manager`, `user permission`, `website`, `builder`, `webstore` all return nothing in the 2026-09-05 applet registry export). Treated as `page_type: applet-feature` with `parent_page` = the CP Commerce Admin page, the same shape as push-notification-configuration. [src:planning/private/registry-applets-2026-09-05.tsv]
- 2026-09-06 — The screen is driven by five values in `bl_cms_website_hdr.property_json.website_builder_config`: `applet_hdr_guid`, `applet_catalog_guid`, `applet_catalog_link_guid`, `tenant_guid`, `app_mst_role_guid`. They are declared in `WebsiteBuilderConfigModel`, resolved by `websiteBuilderConfig()` and consumed by the component — but **nothing anywhere writes them**: a repo-wide grep for `website_builder_config` across all of `refs/` finds only readers (base app plus three customer forks). They must be set through the website API. [src:refs/wavelet-cp-commerce/src/app/models/website-builder-config.model.ts] [src:refs/wavelet-cp-commerce/src/app/utils/resolvers/website-setting-resolvers.ts]
- 2026-09-06 — Without `app_mst_role_guid` the component returns before sending the listing query (`console.warn` only), so the Admin Users card shows the empty state however many admins exist. [src:refs/wavelet-cp-commerce/src/app/pages/website-builder/webstore/user-permission-manager/user-permission-manager.component.ts]
- 2026-09-06 — Tile visibility is `bl_cms_website_ext.param_code = 'HIDE_USER_PERMISSION_MANAGER'` with `value_string === 'true'`, default false. It is one of only two of the thirteen dashboard tiles with **no checkbox** in CP Commerce Admin (`HIDE_HIGHLIGHT_ACTIVITY_MANAGER` is the other); eleven `hide*` checkboxes render in `website-edit.component.html` and are persisted by `website.effects.ts`. Neither of the two missing codes is declared in the shared `BLCmsWebSideExtParamCodes` enum — the storefront reducer reads them as bare string literals. Hiding removes the tile only; the route still resolves. [src:refs/wavelet-cp-commerce/src/app/state-controllers/website-configuration/reducers/website-configration.reducer.ts] [src:refs/blg-applets-wavelet-cp-commerce/micro-fe/projects/akaun-platform/applets/cp-commerce-admin-applet/src/app/components/website-container/website-edit/website-edit.component.html] [src:refs/blg-akaun-ts-lib/projects/blg-akaun-ts-lib/src/lib/sdk/CPCommerce/cp-commerce-constants.ts]
- 2026-09-06 — `WebsiteBuilderGuard` returns `true` for any URL containing `/page/website-builder/layout-menu` before its admin-mode test can apply — and every child route matches — so the client-side gate is effectively "is logged in". All real protection is server-side. [src:refs/wavelet-cp-commerce/src/app/guards/website-builder.guard.ts]
- 2026-09-06 — Website Builder "admin mode" = `userCanMakeChanges` = a non-empty applet token, fetched once per session by `SessionWebsiteAccessEffects` from `core2/tnt/dm/get-applet-token/login-ep` for `environment.cpCommerceAdminAppletCode` (`cp_commerce_admin_console_v1` in dev and prod; `CPCommerceAdminConsole` in the staging environment file, which has no registry row). The token endpoint resolves purely from `bl_applet_login_subject_link` (status != DELETED) joined to tenant and applet — no role, no permission. [src:refs/wavelet-cp-commerce/src/app/state-controllers/session-store/effects/session-website-access.effects.ts] [src:refs/blg-akaun-platform-java/akaun-api/src/main/java/app/api/core2/controller/tenant/dm/applet/GetAppletTokenController.java] [src:refs/blg-akaun-platform-java/javasdk/src/main/java/com/bigledger/core2/dal/uow/applet/AppletLoginSubjectLinkUow.java]
- 2026-09-06 — **Remove Access deletes the role link only** (`DELETE core2/tnt/dm/iam/team-role-links/user-to-role/{guid}`); it never calls uninstall. Because access depends on the applet link, a removed person keeps CP Commerce Admin and keeps admin mode in the Website Builder. Only Tenant Admin can uninstall the link. [src:refs/wavelet-cp-commerce/src/app/pages/website-builder/webstore/user-permission-manager/user-permission-manager.component.ts]
- 2026-09-06 — **Make Admin does not make a tenant admin.** The `rank: 'ADMIN'` in the payload is the applet-link rank. The tenant link (`app_mst_link_login_subject_to_tenant`) is created by `TenantUserService.addUser(..., Optional.of("GUEST"))` when the person is not yet in the tenant. The endpoints this screen uses require rank `ADMIN`/`OWNER` on that tenant link, so somebody promoted here cannot promote anyone else. [src:refs/blg-akaun-platform-java/javasdk/src/main/java/com/bigledger/core2/domain/tenant/TenantUserConfigurationService.java] [src:refs/blg-akaun-platform-java/javasdk/src/main/java/com/bigledger/core2/domain/user/UserPermissionService.java]
- 2026-09-06 — Server-side authorisation, per call: install (`POST core2/platform/dm/akaun-ng/user-applet-links/tenant-admin-ep/{tenantCode}/multiple-install`) = rank ADMIN/OWNER **or** platform sysadmin; invitation (`POST core2/platform/dm/users/send-invitation/tenant-admin-ep/{tenantCode}`) = rank ADMIN/OWNER only; role create/delete = tenant owner/admin **or** `TNT_LOG_TEAM_ROLE_ASSIGNMENT_OWNER` / `TNT_LOG_TEAM_ROLE_ASSIGNMENT_ADMIN` / `TNT_API_TEAM_ROLE_ASSIGNMENT_CREATE` / `..._DELETE`. [src:refs/blg-akaun-platform-java/akaun-api/src/main/java/app/api/core2/controller/platform/dm/applet/UserAppletLinkController.java] [src:refs/blg-akaun-platform-java/akaun-api/src/main/java/app/api/core2/controller/platform/dm/user/PlatformTenantUserController.java] [src:refs/blg-akaun-platform-java/akaun-api/src/main/java/app/api/core2/controller/tenant/dm/user/TenantUserTeamRoleAssignmentController.java]
- 2026-09-06 — Both role-link writes are audited in the tenant DB as `app_user_audit_trail` rows of type `LINK_SUBJECT_TO_ROLE`, event `LINK_ADDED` / `LINK_DELETED`. (Contrast with `bl_applet_audit_trail`, which is not written by role changes.) [src:refs/blg-akaun-platform-java/javasdk/src/main/java/com/bigledger/core2/domain/tenant/TenantUserTeamRoleService.java]
- 2026-09-06 — Verify User = `GET core2/dm/app-login-principal/query` with `principal_type = 'EMAIL_USERNAME'` and `principal_id = <address>`. The SQL is `principal_id = :principal_id` — exact and case-sensitive — and excludes DELETED. It searches the **master** database, so a green tick means "an Akaun account exists somewhere on the platform", not "in this tenant". [src:refs/blg-akaun-platform-java/javasdk/src/main/java/com/bigledger/core2/dal/uow/identity/AppLoginPrincipalUow.java]
- 2026-09-06 — Rows the caller may not read are **masked, not withheld**: `replaceAppLoginPrincipalWithoutPermission` returns guid + `status = PERMISSION_DENIED` with no subject guid, so `totalRecords` is non-zero and the component throws "User subject GUID not found in response" and stops with no message. The same pattern applies to the Admin Users listing (`app_mst_link_subject_to_role` masked to guid + `PERMISSION_DENIED`). [src:refs/blg-akaun-platform-java/akaun-api/src/main/java/app/api/core2/controller/platform/dm/applogin/AppLoginPrincipalController.java] [src:refs/blg-akaun-platform-java/akaun-api/src/main/java/app/api/core2/controller/tenant/dm/user/TenantUserTeamRoleAssignmentController.java]
- 2026-09-06 — The component has **no error UI at all**: every catch ends in `console.error` and a state reset. There is no toast, no inline error. Every server failure looks identical to the user ("the button did nothing"). [src:refs/wavelet-cp-commerce/src/app/pages/website-builder/webstore/user-permission-manager/user-permission-manager.component.ts]
- 2026-09-06 — The *User* column is always the e-mail local part: `enrichUsersWithDetails` overwrites `name` with `principal_id.split('@')[0]` for every row, so the account's real display name never appears. The *Status* column is the role-link status, not the account status. Page size is fixed at 10; detail lookups batch 20 subject guids. [src:refs/wavelet-cp-commerce/src/app/pages/website-builder/webstore/user-permission-manager/user-permission-manager.component.ts]
- 2026-09-06 — Send Invitation posts `postRegistrationRequest.add_user_to_tenant: true`. `PostRegistrationService` then runs `stepAddUserToTenant` only — the tenant link at rank GUEST. No applet, no role: the operator must return and press Make Admin. Default e-mail subject "Invitation to AKAUN", overridable per tenant through `MessagingChannelService` (`EMAIL_USER_INVITATION`); the link points at `core2/platform/dm/identity/registration/user_confirmation_redirection` with the verification code, registration key and address. [src:refs/blg-akaun-platform-java/javasdk/src/main/java/com/bigledger/core2/domain/platform/identity/PostRegistrationService.java] [src:refs/blg-akaun-platform-java/javasdk/src/main/java/com/bigledger/core2/domain/tenant/UserInvitationService.java]
- 2026-09-06 — Make Admin is two calls, not one transaction. The role step rejects a duplicate with `CLIENT_LINK_EXISTS`, a missing/inactive role with `CLIENT_ROLE_VALIDATOR_GUID_IS_INVALID`, and an unknown subject with `LOGIN_SUBJECT_GUID_IS_INVALID`; when it fails the applet stays installed. The install step is idempotent (existing link is updated, keeping the higher rank). [src:refs/blg-akaun-platform-java/akaun-api/src/main/java/app/api/core2/controller/tenant/dm/user/TenantUserTeamRoleAssignmentController.java] [src:refs/blg-akaun-platform-java/javasdk/src/main/java/com/bigledger/core2/domain/platform/applet/UserAppletLinkService.java]
- 2026-09-06 — 0 rows in `bl_applet_client_side_perm_dfn` for `cp_commerce_admin_console_v1` (carried forward from the CP Commerce Admin page, run 1). Nothing on this screen is gated per role client-side.

## How it connects

- **cp-commerce-admin-applet** — the applet this screen grants, and the owner of the Website record it reads. Its *Website → Details* tab holds the eleven tile-hiding checkboxes; the two missing codes belong there.
- **tenant-admin-applet** — creates the role, holds the tenant ranks these endpoints check, and is the only place an applet link can be uninstalled (which is what actually revokes access).
- **push-notifications** — the same anti-pattern: a Customer Portal feature whose only configuration lives in `bl_cms_website_hdr.property_json` with no screen to set it.
- **client-side-permissions** — not used here; the whole feature is rank- and tenant-permission-based, master DB for the applet link, tenant DB for the role link.

## Open questions

- Which principal(s) actually hold `MST_API_APP_LOGIN_PRINCIPAL_READ` in a normal tenant? The masking path is reachable, but who hits it in practice is unverified (no tenant data queried).
- Was the omission of `HIDE_USER_PERMISSION_MANAGER` (and `HIDE_HIGHLIGHT_ACTIVITY_MANAGER`) from the admin checkboxes deliberate, or is it an oversight from when the two tiles were added?
- Should Remove Access also uninstall the applet link? As written the button's promise ("this action cannot be undone", "the user can no longer access admin features" in the old wiki page) is not what the code does.
